# Cache layers and latency plan

Status: answer cache and five intermediate cache layers are implemented in v2.8 and measured on the pinned five-question set. Langfuse cache hit/miss I/O was inspected. Live app deployment and Redis restart persistence still need verification. Updated 2026-10-21.

## Decision

The current default is v2.8, based on v2.7. It keeps the exact-answer cache and adds query, embedding, search, rerank, and tool-read caches. Cache controls remain request-scoped, outside saved pipeline settings.

An answer becomes reusable when its answer-correctness score is **0.90 or higher** or the user gives it a thumbs-up. Citation-support scores do not determine cache eligibility. A thumbs-down on an answer served from cache removes that entry when it is still the version served.

## Five-item cache check

The first five items in the same pinned QA.csv snapshot were run with `refresh`, then repeated with `use` against an empty disposable Redis instance. Both runs used v2.7 and the same dataset version. `refresh` always generated answers and wrote only answers that passed the correctness gate; the repeat produced one cache hit and four misses.

| Pass | Answer-generation latency | Agent model calls | Mean correctness | Mean citation support |
| --- | ---: | ---: | ---: | ---: |
| Refresh, 5 generated | 24.07 s mean | 37 | 0.8567 | 0.600 |
| Use, 1 hit + 4 generated | 25.40 s mean across misses | 35 across generated answers | 0.8667 | 0.500 |

The affair question was the one hit. Its refresh answer scored 0.9833 for correctness and 0.5 for citation support, so it was eligible as intended. This five-item run used the previous threshold (>0.95): the cigarette-case question scored exactly 0.95 on refresh and was not eligible under that rule; its later miss scored 1.0 and became eligible after that run. The threshold has since changed to >=0.90, under which that 0.95 result and the answers scoring 0.90 also qualify; under the current gate, four of the five refresh answers meet the threshold. At the time of this five-item check, the experiment artifact did not record lookup latency for hits, and miss latency varied substantially across passes. A follow-up single-question check below records the lookup time. The five-item result remains a functional check, not a general performance conclusion.

## Intermediate cache layers

The five intermediate layers cache deterministic pipeline work under the resolved project, corpus, pipeline, prompt, model, and index identity. `query` caches query rewrites and name completion; `embedding` caches query vectors; `search` caches dense and keyword results; `rerank` caches cross-encoder scores; `tool_read` caches read-tool results and the evidence/focus state needed to replay them. These layers are not gated by answer correctness. The 0.90 correctness threshold or a thumbs-up applies only to the exact-answer cache; citation scores do not affect that gate.

Intermediate entries use the `pipeline-cache:v1` namespace and expire after 30 days. `refresh` computes and stores selected intermediate layers; `use` reads them and stores misses; `bypass` skips Redis. Redis errors fail open and leave normal computation in place. An unspecified interactive `cache_layers` setting enables all supported layers. Experiments still bypass caching unless a mode is requested.

Each intermediate operation opens a Langfuse span before the lookup and computation. The finished span name includes the layer and status, such as `cache hit: rerank`; input, output, lookup duration, compute duration, saved duration, and write status are recorded. A hit's input/output is the same content as the corresponding miss operation.

### Combined default-agent pass

The combined default-agent pass used the same five questions with answer caching excluded. Query rewrite is not called by this v2.8 agent. It recorded 32 hits across embedding (8), search (8), rerank (8), and tool reads (8). Those hits avoided 4.469 seconds of measured compute. Redis lookup took 0.011 seconds; tool-state replay added about 0.030 seconds, for approximately **4.43 seconds of net intermediate work saved**. Correctness was 0.8767 (refresh: 0.8567); citation support was 0.700 (refresh: 0.600). These score differences are run-to-run answer variation, not a cache effect.

The rewrite-path pass used fixed v1 with query, embedding, search, and rerank enabled together. All 154 recorded layer operations hit: query 21, embedding 37, search 72, rerank 24. They avoided 48.440 seconds of measured compute for 0.022 seconds of Redis lookup, or **48.418 seconds net** across the five questions. Correctness was 0.850 in both refresh and use; citation support was 0.900 in both. Trace input/output comparison found no differences for hits with a corresponding refresh operation. The Langfuse client emitted repeated “attributes dict is full” warnings during this long trace; cache spans and metrics were still present, but this metadata pressure should be addressed before relying on these traces for long-term observability.

## Behavior

- Interactive requests use the cache by default. The API accepts `cache_mode` values `use`, `bypass`, and `refresh`, plus `cache_layers` for `answer`, `query`, `embedding`, `search`, `rerank`, and `tool_read`.
- Dataset experiments bypass the cache by default. The selected correctness evaluator's score controls writes to the answer layer only. Citation support is recorded but ignored by the answer eligibility gate.
- `bypass` neither reads nor writes cache entries. `refresh` recomputes selected layers; answer results wait for approval while intermediate results are stored immediately. `use` reads selected layers and writes intermediate misses.
- A cache hit creates a fresh Langfuse trace linked to the source trace and returns the answer promptly, including on the streaming endpoint.
- If Redis is unavailable, normal pipeline work continues without the cache and the trace records the cache status.
- The web UI has no cache controls. Its existing thumbs-up feedback promotes that answer; thumbs-down feedback invalidates a currently served cached answer.

## Storage, identity, and maintenance

Redis runs as its own Compose service using `redis:8.2.10-alpine`, append-only persistence, a dedicated named volume, and a loopback-only published port. Use `redis-py`. Do not set `maxmemory`; monitor host memory and disk. Approved answer entries have no expiry. Unapproved feedback candidates, served-answer feedback links, and intermediate entries expire after 30 days.

Every answer key includes the stable project ID, corpus ID, pipeline version and fingerprint, resolved pipeline ID, corpus checksum, profile and prompt identities, index collection, resolved model/configuration identities, cache format, and exact question text. Pipeline versions and projects cannot share keys. Runtime identity comes from the active corpus and pipeline configuration.

Local maintenance commands inspect cache size by project, corpus, and pipeline, and clear a question or scope. Scoped deletion requires project and corpus IDs; whole-cache deletion must be explicit:

```bash
python -m app.answer_cache stats
python -m app.answer_cache clear --project-id millenium --corpus-id millennium --pipeline-version v2.8 --question 'Who is Lisbeth Salander?'
python -m app.answer_cache clear --all
```

Use `redis-cli BGREWRITEAOF` to compact persistence after large deletions. Preserve the named volume during ordinary redeploys; removing it deletes the cache.
