# Speed up the agent pipeline with optional caching (v2.8)

Status: planned. Updated 2026-10-21.

## What we are trying to improve

Questions in the v2.2 agent pipeline often take around 20 seconds and can take much longer. In a previous 35-question run, the median was 20.7 seconds, the slowest 10% took more than 43.4 seconds, and the longest took 71.7 seconds. Model calls accounted for most of the wait; recorded tool work averaged about 1.5 seconds per question.

Version v2.6 has since been released as the v2.2-compatible pipeline with selectable OpenAI query-agent and automatic-scene-search options. Build the cache variant as **v2.8** from v2.6, keeping v2.2 and v2.6 available for comparison. Do not change either released pipeline.

This app has few visitors, so normal traffic is unlikely to produce many cache hits. We will measure speed using controlled repeat questions and time every model request. Caching is still useful for repeated questions, experiments, and repeated work within a question. It is optional at every layer.

## How people will use the cache

- **Normal interactive question:** use the enabled caches.
- **Dataset experiment:** skip caches by default, with an option to turn them on for a specific run.
- **Interactive question starting with `/nc`:** skip all application caches and use a separate, cold Ollama service. For example, `/nc What happened in chapter 4?` asks the same question without cached results. Remove `/nc` before the agent sees or records the question. This command is a convenience, not a security feature. Existing rate limits still apply.
- **API request:** accept a cache mode of `use`, `bypass`, or `refresh`, plus an optional list of cache layers. `bypass` neither reads nor writes cached results. `refresh` recomputes results and replaces selected entries. An optional `cold_model` flag uses the separate Ollama service. Put these controls on the request, outside the saved pipeline settings.
- **Local maintenance:** provide a command to clear one question, one layer, one pipeline version, one corpus, one project, or the whole cache. Do not expose a public cache-clearing endpoint or add cache controls to the web UI.

## What we will cache

Run Redis in its own Docker Compose service using the official `redis:8.2.10-alpine` image; the app connects to it with `redis-py`. Publish Redis on `127.0.0.1:6379` so it is reachable by the app container, which currently uses host networking, but is not exposed on other network interfaces. Mount a dedicated named Docker volume, such as `redis_cache_data`, at Redis's data directory. Enable append-only persistence (`appendonly yes`) so Redis reloads cached entries from that volume after a container restart or machine reboot. Set `restart: unless-stopped` so Docker starts Redis again after boot unless an operator has explicitly stopped it. Do not remove the volume during normal redeploys; deleting the volume (for example, with `docker compose down -v`) deletes the cache. With Redis's usual once-per-second disk sync, a sudden power loss may lose about the last second of writes.

Do not set a Redis `maxmemory` cap initially. Expected traffic and cache volume are low, so a fixed limit would add unnecessary configuration. Redis shares the host's RAM with the app and Ollama, so monitor memory and disk use as part of operating the service.

If Redis is unavailable, normal requests should still run without cached results. Record the failure in the trace.

| Layer | What can be reused | Safeguard |
| --- | --- | --- |
| Final answer | The answer and its citations for the exact same question | Save only answers with valid citations and a positive evidence check. Do not save abstentions, forced answers, failed checks, or answers changed after the check. A cache hit still gets a new trace linked to the original run. |
| Query preparation | Repeatable model outputs such as query expansion | Include the full input, prompt, model, and generation settings in the cache key. Do not cache the agent's changing decisions. |
| Embeddings | Vectors for the same query text | Include the embedding model version in the key. |
| Search | Results of the same vector, scene, or keyword search | Include the collection, index version, and search arguments in the key. |
| Reranking | Scores for the same query and document pairs | Include the reranker model version and the order of the pairs. |
| Tool reads | Results from tools that return the same output for the same input | Include the tool arguments and corpus version. On a hit, rebuild the current agent's evidence and focus from the cached result; do not store and replay the whole changing agent state. |

### Only keep results from approved answers

Make a question's results eligible for reusable caching only when its final answer scores **above 0.95** or the user gives that answer a thumbs-up in the interface. This rule applies to every cache layer, including intermediate results such as embeddings, searches, and tool reads. Since those results are produced before the final answer is scored, hold their cache writes until the answer qualifies. A thumbs-up should also make that run's held results eligible. Existing cache hits may be used to answer a new question; only results from qualifying runs are added to or refreshed in the cache. Keep the existing citation and evidence checks for final-answer caching as additional requirements.

### Keep projects and corpora separate

The cache must work with the planned multi-corpus project structure, where shared pipeline versions can run against different corpora and generated data lives under `data/<corpus-id>/`. Prefix every Redis key with a stable project or deployment ID, a corpus ID, and the selected pipeline version, for example `project/millennium/corpus/corpus-a/pipeline/v2.8/search/...`. Every pipeline version gets its own namespace across all cache layers, so entries cannot cross version boundaries. This is a version boundary applied to each cache layer, not another cache layer. Do not rely on the current default corpus or a global Redis database number to separate results. For normal requests, resolve these IDs from the selected project, corpus, and pipeline configuration; local maintenance commands must require the relevant IDs.

Within that namespace, include the cache format, pipeline version and fingerprint, corpus source checksum, corpus profile and prompt identities, model versions, and the exact layer inputs. Search and tool results must also include the corpus's index or collection identity. This keeps one corpus or project's answers, search results, and indexes from being returned for another. When source material, profile, prompts, models, or indexes change, the new identities prevent reuse of old entries; the old entries remain until explicitly cleared.

Runtime cache operations use the project and corpus IDs resolved from the active configuration. Local invalidation must name its target project or corpus so it cannot clear another scope by mistake; a whole-cache clear is an explicit maintenance operation. If a future cache layer is intentionally shared across corpora, document and test why its value is corpus independent before removing the namespace.

Cache entries do not expire automatically. Keep them until a local invalidation command removes them. Keep the existing in-process and index-building caches, ensuring any corpus-specific entries follow the same project and corpus scope.

### Risks of keeping entries indefinitely

- **The cache can grow over time.** Entries have no expiry and Redis has no configured memory cap, so cache data can consume more host RAM and the persistent volume can consume more disk space as use grows. Monitor both and use the scoped invalidation commands above if cleanup is needed. If Redis does run out of memory or disk space, requests should still complete without caching and the failure should be visible in the trace.
- **Old entries can remain on disk.** Redis persistence stores data in its Docker volume. Deleting old keys from Redis may not immediately shrink the append-only file; include a safe way to compact it and monitor free disk space.
- **A cache key bug can serve stale or cross-corpus results.** Include the full project, corpus, source, profile, prompt, model, index, and pipeline identities described above. When any identity changes, new requests must use a different key. Explicitly clear affected scopes when correcting a key or cache bug.
- **Old versions consume space.** Keeping entries forever also keeps results for old pipeline and model versions, even when they are no longer used. Provide commands to inspect cache size by project, corpus, pipeline, and layer, and remove obsolete scopes deliberately.
- **Cached answers are retained data.** Apply the app's data access and backup practices to the Redis volume, and make broad deletion available for maintenance.

No-expiry means entries have no time limit; it does not mean they are guaranteed to remain available. A Redis volume can be lost, or writes can fail if the host runs out of memory or disk space.

For each layer, record whether the request found a cached result, missed, bypassed the cache, refreshed a result, or continued after a Redis failure.

## What `/nc` means for Ollama

Skipping Redis alone does not make a model call cold: Ollama can keep a model loaded and reuse prompt work. Add a second Ollama service at `127.0.0.1:11435` for controlled cold runs. It shares the model files with the regular service and handles one request at a time. Route **every** model call in an `/nc` question through it, including preliminary checks and calls made by tools. Unload any model already in that service before the question; use `keep_alive: 0` so each call unloads afterward. Leave the regular Ollama service alone. If the separate service is unavailable, return a clear error.

`/nc` is intentionally slower. It skips application results and Ollama's loaded-model and prompt reuse. It does not rebuild the search indexes or clear the operating system's file cache. Ollama documents `keep_alive: 0` in its [FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx).

## Measure, compare, then roll out

1. **Measure every model call.** Record why it was made, which model was used, total time, model load time, input tokens, reused input tokens, time spent processing input, output tokens, and time spent generating output. Include preliminary checks and model calls inside tools. Ollama provides the underlying [usage fields](https://github.com/ollama/ollama/blob/main/docs/api/usage.mdx).
2. **Add the optional cache layers and controls.** A cached answer must still have a fresh trace and accept feedback. If the answer is streamed, send the cached text promptly instead of delaying it word by word.
3. **Compare v2.6 and v2.8 on the same questions.** Run cold, warm, refreshed, and `/nc` cases. Report typical and slow-question times, time spent in model calls, cache use, and any answer or citation differences. Controlled runs matter more than waiting for enough production traffic.
4. **Check failure and change cases.** Check citation validity; changes to models, prompts, and indexes; each cache-clearing option; a Redis outage; an outage of the separate Ollama service; and experiments running at the same time. Confirm dataset experiments bypass caches unless explicitly opted in.
5. **Choose the default after review.** Consider making v2.8 the interactive default only if the quality and latency results support it. Keep v2.2 and v2.6 selectable.

Caching mainly saves repeated work. The model timings will show what to improve next for brand-new questions, such as the number of agent turns, prompt size, model choice, or model loading.
