# Millennium RAG experiment setup

## Current workflow

New runs default to `retrieval_mode: "full"`: search the original question, a HyDE hypothetical document, three distinct literary query alternatives, and a grammar-corrected question. Each query is embedded and searched separately; reciprocal rank fusion merges the candidates before cross-encoder reranking and evidence-grounded answer generation. Use an explicit `baseline`, `hyde`, `query_expansion`, or `hyde_query_expansion` config for component comparisons. Grammar correction is included in `full`.

The runtime prompts are `rag-answer`, `rag-hyde`, `rag-query-expansion`, and `rag-grammar-correction`. Edit them in Langfuse **Prompts**, save a new version, and assign the `production` label (or pass a different `prompt_label`). Each experiment and `/ask` request fetches the selected label with the SDK cache disabled, pins the returned versions, and links generation observations to those prompts. Changes during an experiment take effect on the next run.

The judge definitions are edited in Langfuse **Evaluators**: `millennium-answer_correctness_v1`, `millennium-answer_correctness_v2`, `millennium-answer_correctness_v3` and `millennium-citation_support_v1`. Runs use `answer_correctness_v3` by default: the judge marks each of the item's `required_facts` and `supporting_details` (from the expected output; maintained in `datasets/answer-facts.json` and uploaded as a new dataset version with `python app/answer_facts.py --apply`) present, partial or missing, and the code scores required facts at 90% and details at 10%. v3 runs through a local `opencode serve` (`deepseek-v4.1-flash-free`, variant `low`); pass `correctness_evaluator: answer_correctness_v2` for the local Ollama judge, or `answer_correctness_v1` for the old single-score judge. v3 is a local-only evaluator: its Langfuse object stays active with the project's `ollama-local` connection as a registry placeholder, while the runner executes it through `opencode serve` based on `JUDGE_MODELS`. Do not assign a managed Langfuse rule to v3; that would run the placeholder model and duplicate the local score. Start `opencode serve` with `OPENCODE_JUDGE_URL` (default `http://127.0.0.1:4096`) before running v3. Design, rollback versions and trial results: `docs/plans/2026-10-19-answer-correctness-v2.md`. The runner pins their current definitions and uses their actual prompt messages and model names when calling local Ollama. It validates the numeric 0–1 contract and supported variables, without comparing editable rubric text to Python templates. The old `rag-eval-*` Prompt entries are retained for historical runs and are no longer the source of judge instructions. Native UI tests use the `ollama-local` model connection through the authenticated gateway. The experiment runner automatically executes both judges and uploads scores; additional automatic Langfuse rules are unnecessary and would duplicate evaluation.

Every dataset item has a stable, readable session: its question number and the first 45 characters of the question in kebab case, e.g. `QA1-did-salander-and-mikael-have-affair`. The number is the item's CSV data row (`source_row` − 1); an item added in Langfuse can set its own with `{"label": "QA36"}` in its metadata, otherwise it is named after its item ID. Runs before 2026-10-15 used `qa-<dataset-id>-<item-id>` sessions; on 2026-10-15 those were renamed in place in Langfuse's ClickHouse (`events_full`, `events_core`) and tagged, with the original rows and the old-to-new mapping kept in the `session_rename_backup_20261015` database. Older execution records under `data/` still show the old session names. Each run trace is also tagged `question:QA1`, and its scores filter on that tag: a dashboard line chart of a score over time, filtered by trace tag `question:QA1`, shows how that question's score moved across runs. Open **Sessions** (widen the date range: the list filters by when a session was created), select a question session, and expand a run trace to see the root, all query transformations, six searches and their embedding observations, fusion, reranking, evidence formatting, answer generation, citation extraction, and both judges. Experiments and their scores use `sdk-experiment`; interactive requests use `default`. These are tracing environments, not retrieval variants. `/ask` accepts an optional `session_id`; otherwise it groups repeated normalized questions under a stable `interactive-...` session. The web UI groups questions into one session per client IP, `ui-<ip>` with dots as dashes (e.g. `ui-78-163-48-13`); an IPv6 client is named after the first four groups of its address (e.g. `ui-2a00-1d34-cf1e-9701`), because devices rotate the rest, and records the browser's random cookie ID as the trace's user ID; a browser may view and rate only traces with its own user ID. Older web UI traces were moved into their IP sessions on 2026-10-15 (backup tables `ui_events_full`/`ui_events_core` in `session_rename_backup_20261015`); traces recorded before client IPs were captured keep their `interactive-ui-<uuid>` session.

**Run an experiment on the latest pipeline:** in Langfuse open **Datasets → QA.csv → Run experiment** (remote), and use
an empty payload:

```json
{}
```

That always runs the deployed app's current pipeline with its default settings and the `production` prompts. Add only
a name if you want one, e.g. `{"variant_label":"my-test"}`; any `config` or `prompt_label` makes it a variant instead.

Or run `python app/experiments.py --dataset QA.csv --variant full-retrieval`. To compare a baseline, explicitly pass a config file containing `{"retrieval_mode":"baseline"}`. Reference answers are provided only to the correctness judge, never to retrieval or answer generation.

## Stage 1 setup

Create a Python environment and install the SDK release verified against this machine's Langfuse instance:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r app/requirements.txt
cp -n .env.example .env
```

Set the project-scoped `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` in `.env`. Keep `.env` local. Langfuse should be reachable at `http://127.0.0.1:28420` from the host. The required hosted project is named `millenium`; the dataset is named `QA.csv`.

Check project/dataset access without changing Langfuse, then seed the target-root CSV once:

```bash
set -a; . ./.env; set +a
python app/seed_dataset.py --check-only
python app/seed_dataset.py
```

The seed command validates all rows before it writes, assigns deterministic UUIDv5 item IDs, maps questions to `input.question` and references to `expected_output.answer`, and records the CSV checksum and row provenance. It saves its import mapping under `EXPERIMENT_DATA_DIR` (default `./data`). On a later invocation it verifies the original rows without updating them. If a dataset already contains items but has no local seed mapping, the command refuses by default; `--reconcile-existing` permits an explicit check of deterministic seed IDs and provenance and can finish a partial first import. Once the original mapping exists, added Langfuse items are allowed, while missing seeded items are reported and never recreated. Edit live QA cases in Langfuse after the initial import.

The evaluator rubric specifications and typed configuration/identity helpers live in `app/evaluator_specs.py`, `app/resolved_config.py`, and `app/identity.py`. The four runtime prompts and four evaluator definitions (answer correctness v1, v2, v3 and citation support v1) are managed in Langfuse. The default prompt label is `production`; every execution fetches that label once, records immutable prompt IDs/versions, and uses the fetched templates for generation and judging. `EVALUATOR_MODEL` is separate from `GENERATION_MODEL` and defaults to `qwen3:8b`. `EVALUATOR_OLLAMA_URL` optionally selects a separate endpoint for local judge calls; if unset, evaluators use `OLLAMA_URL`. Set `OLLAMA_CONTEXT_LENGTH=8192` on the host Ollama service: the pipeline calls with `num_ctx: 8192` while judge calls use the default, and qwen3:8b reloads for about 2 s on every switch otherwise. With a uniform context the switches cost under 0.1 s.

Reconcile the Langfuse asset catalog explicitly after deployment. A read-only run reports missing or mismatched assets. Creation is opt-in; updates create new versions only when explicitly requested:

```bash
set -a; . ./.env; set +a
python app/prompt_assets.py
python app/prompt_assets.py --create-missing
python app/prompt_assets.py --create-new-versions
python app/prompt_assets.py --label staging --create-missing
```

The runtime prompts are `rag-answer`, `rag-hyde`, `rag-query-expansion`, and `rag-grammar-correction`. Evaluator objects are `millennium-answer_correctness_v1`, `millennium-answer_correctness_v2`, `millennium-answer_correctness_v3` and `millennium-citation_support_v1`; their stable IDs and versions are resolved from the Langfuse v2 evaluator API before a run starts. Local Ollama executes the v1/v2/citation prompts; v3 runs through a local `opencode serve` because the free opencode tier only serves requests made from inside opencode. The project also has an `ollama-local` Langfuse LLM connection for Playground and other UI workflows, but this local evaluator path does not use it. v3's Langfuse object is active with the `ollama-local` connection as a registry placeholder; `JUDGE_MODELS` selects the real opencode execution. Preflight still accepts a paused opencode evaluator if that connection is removed. The evaluator objects remain the versioned canonical rubric/output/model definitions. Do not run managed evaluator rules in parallel with the local path, which would duplicate scores. Promote prompt labels in Langfuse deliberately; choose another label with `--prompt-label` for a CLI run or `prompt_label` in the trigger payload. Missing labels/assets, inactive evaluators, and incompatible score contracts fail preflight. Prompt and rubric edits are accepted.

## Callback routing

The current Langfuse Docker UI only accepts webhook URLs on ports 80 and 443 and blocks private destinations by default. In the local Langfuse deployment, `LANGFUSE_WEBHOOK_WHITELISTED_HOST=172.18.0.1` permits the bridge hostname, and the `langfuse-webhook-proxy` service binds only to `172.18.0.1:80` and forwards `POST /experiments/run` to the app on `127.0.0.1:8001`. Configure the dataset webhook URL as `http://172.18.0.1/experiments/run` and add `X-Experiment-Trigger-Token` with the same value as `EXPERIMENT_TRIGGER_TOKEN`. Keep request signing disabled unless `LANGFUSE_WEBHOOK_SECRET` is also set in the app environment. Langfuse sends `projectId`, `datasetName`, `datasetId`, and a `payload` value; version 4.59 sends that payload as a JSON string, which the handler decodes, while also accepting an object and `customPayload` for compatible callers. Payload fields are `variant_label`, `config`, optional `dataset_version`, `item_ids`, and `prompt_label`. The bridge address is deployment-specific and must be rechecked after network changes.

## Stage 2 implementation

The target app exposes `/ask`, `/index`, and the experiment API from `app/main.py`. Interactive calls and dataset tasks share `app/pipeline.py::run_pipeline(question, config)`. `/ask` defaults to full retrieval, 1200-character passages built by joining paragraphs to at least 400 characters, 30 fused candidates, and 10 evidence passages; when no reranked passage scores at least `low_confidence_score` (2.0), it uses `low_confidence_top_k` (15) passages and lets the answer model reason before answering. Each search also returns its top `wide_candidate_count` (100) hits; when the best fused candidate scores below `wide_trigger_score` (3.5), wider-pool passages that the cross-encoder scores above every fused candidate and above `low_confidence_score` are placed in front of the usual evidence (at most `wide_max_hits`, 3), which is otherwise unchanged. A strong fused candidate can be on topic without answering, so above that score a wider-pool passage is still admitted when it beats every fused candidate by more than `wide_override_margin` (2.0). When the question uses a bare name the books rarely use alone (e.g. "Mikael"), name completion searches the completed wording ("Mikael Blomkvist") as well; its hits join the wider pool, which is then scored against the completed wording and must also beat every fused candidate scored against it. Some answers are a whole scene of dialogue that never names the people involved, so no single passage matches the question; a second index holds LLM summaries of every window of `scene_window` (6) consecutive passages of one EPUB section, every `scene_stride` (3) passages. Unless the evidence is weak (the low-confidence path), the question is matched against these summaries, and the passages of the best-matching scene are added after the usual evidence when its summary beats every scene the top evidence already comes from by more than `scene_margin` (1.0) and scores above `low_confidence_score`. It requires the matching index to be ready and does not rebuild an index during a question request.

Start the Docker services after setting `.env` and the trigger token:

```bash
cp -n .env.example .env
# Set Langfuse project keys and a long random EXPERIMENT_TRIGGER_TOKEN in .env.
docker compose up --build -d
```

Build the default index once. Each indexing configuration receives its own content-addressed Qdrant collection; the manifest and point counts are stored in `data/experiments.sqlite3`.

```bash
curl -sS -X POST http://127.0.0.1:8001/index \
  -H 'Content-Type: application/json' -d '{}'
```

An interrupted or failed index is left incomplete and will not be silently reused. To explicitly rebuild that same index identity, pass `{"explicit_rebuild":true}` with the same `config` object. Existing other collections are retained.

Ask one interactive question through the shared pipeline:

```bash
curl -sS -X POST http://127.0.0.1:8001/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Did Salander and Mikael have affair?"}'
```

Run all active items from the pinned QA dataset version through the CLI (on the host, activate the app environment and source `.env` first):

```bash
set -a; . ./.env; set +a
python app/experiments.py --dataset QA.csv --variant baseline
```

Use a configuration JSON file to change one component, for example `{"passage_chars":600}`. To run one item, add `--item-id <Langfuse-dataset-item-id>`. To rerun a historical snapshot, pass its UTC timestamp with `--dataset-version '2026-10-14T10:00:00+00:00'`. To pin a non-default prompt environment label, add `--prompt-label staging`. Every invocation creates a new execution ID, run name, and execution directory under `data/executions/`; an item's session ID remains stable across runs. Pipeline identity incorporates the pinned prompt IDs/versions; evaluator identity incorporates the evaluator objects and judging prompt versions.

The run config can vary `retrieval_mode` (`full`, `baseline`, `hyde`, `query_expansion`, or `hyde_query_expansion`), `candidate_count`, `top_k`, `passage_chars`, `min_passage_chars` (join consecutive paragraphs of one section until a passage reaches this length, never past `passage_chars`; a section's last passage shorter than this joins the passage before it, or takes that passage's last paragraphs when the two do not fit, so the line a chapter ends on keeps its context; default 400, set 0 to disable), `passage_overlap` (paragraphs repeated between joined passages; requires `min_passage_chars`), `expansion_count` (query alternatives; a `rag-query-expansion` version may reference `{{expansion_count}}`), `hyde` (default on; false drops only the hypothetical-document query and keeps every other step of the mode; removing it lowered QA.csv correctness 0.764 → 0.722 and cut mean latency by about 3–5 s), `parallel_transformations` (default off; when on, the HyDE, query-expansion and grammar requests run together in a thread pool, so `OLLAMA_NUM_PARALLEL` must allow concurrent requests; each rewrite keeps its Langfuse span under the question's trace), `low_confidence_score` (cross-encoder score below which the top reranked passage counts as weak evidence; null disables the low-confidence path) and `low_confidence_top_k` (evidence passages used, with reasoning, on that path), `wide_candidate_count` (per-search hits fused into a wider pool that is reranked against the question; 0 or a value no larger than `candidate_count` disables it) and `wide_trigger_score` (wider-pool passages are considered only when the best fused candidate scores below this; null always considers them; an admitted passage must beat every fused candidate and `low_confidence_score`, and is added in front of the usual evidence), `wide_override_margin` (above `wide_trigger_score`, a wider-pool passage is still admitted when it beats that bar by more than this; default 2.0, calibrated on QA.csv; null disables) and `wide_max_hits` (most wider-pool passages admitted; default 3, the most any QA.csv question admitted before the cap), `keyword_hits` (default 30, 0 = off; BM25 hits per question from an in-memory keyword index over the passages, stop words dropped and plural -s stemmed; they are reranked against the question and considered only when one beats every fused candidate by `keyword_margin`, default 4.0, calibrated on QA.csv and Additional Questions; then the hits that beat every fused candidate, at most `keyword_max_hits` (5), are added in front of the evidence in reading order, each joined with the passage before it), `scene_margin` (default 1.0, calibrated on QA.csv; null disables scene search), `scene_window` and `scene_stride` (passages per summarised window and the step between windows; `/index` builds the scene index once per passage index, with one summary-model call per window, about 1.7 hours with gemma4:26b for the three books on this machine; summaries are cached in `SCENE_SUMMARY_CACHE`, default `/data/scene-summaries.jsonl`) and `scene_search_hits` (summaries scored per question), `scene_moment` (default on: describe the moment a question asks about, search the scene summaries with it, let the generation model pick the scene and add it with the window that continues it; needs the scene index), `entity_names` (default on: `/index` builds entity cards once per passage index, one `scene_summary_model` call per non-overlapping window of 6 passages listing its people, other names of people, places, companies, vehicles, clothing and objects with the person each belongs to, about 2.8 hours with gemma4:26b for the three books; extractions are cached in `ENTITY_CACHE`, default `/data/entities.jsonl`, and the merged cards are written under `ENTITY_CARDS_DIR`, default `/data/entity-cards`; when the question names a person and its best match among the links into that person, reranked against the question and scoring at least `low_confidence_score`, is another name of that person not already in the evidence, the passages stating that person's other names are added in front of the evidence with a `Link:` line saying whose name each is), `scene_context` (default on, off when `scene_margin` is null since it needs the scene index: `/index` builds a second passage collection embedding each passage with its scene summary cut to the `scene_context_sentences` (2) sentences nearest the passage; per question, that collection is searched with the same queries, every row is reranked with its context in front, and up to `scene_context_max_hits` (2) passages not already in the evidence are added after the usual evidence, before scene passages, when they rank in the top `scene_context_rank` (3) and score above `low_confidence_score`; the later paths do not see them and the answer model sees only book text; on QA.csv it fixed two items and lowered two by answer drift, with no evidence lost), `entity_matrix` (default on; uses the same entity cards: the question's phrases pick kinds of link, edge types such as nickname, vehicle or tattoo, at MiniLM similarity of at least `entity_matrix_similarity`, default 0.75; named entities and their name variants restrict the links; the remaining words are scored against each end's facts, and with neither the links stated in the most windows come first; up to `entity_matrix_max_hits` (8) names add the passage that states them with a `Link:` line, unless the evidence already names the best one; it runs only when `entity_names` adds nothing), `entity_graph` (default off, rejected on 2026-10-18, see IMPROVEMENTS.md: `/index` then also extracts events between people per entity window with the 4,000 characters before it, one `scene_summary_model` call per window, about 2.8 hours with gemma4:26b, cached in `ENTITY_EVENTS_CACHE`, default `/data/entity-events.jsonl`; per question, Personalized PageRank with damping `entity_graph_damping` (0.5) over passages, entity cards and events, seeded by the entities the question names and the evidence, ranks the events; of the best `entity_graph_pool` (30), up to `entity_graph_max_hits` (2) scoring at least `low_confidence_score` add the passage that states them after the usual evidence with a `Link:` line, and `entity_graph_facts` (default 0) adds that many best-matching events as one-line `Event:` evidence entries instead), `keyword_rare_share` (default null = off; a keyword hit with one sentence holding every rare non-name question word, each in fewer than this share of passages, is added at any score), `scene_thinking` (default off; when a scene is admitted, tell the answer model its passages are one continuous scene and let it reason first: more complete answers on QA.csv but no correctness gain, about 50 s more per such question), `scene_summary_model` (the Ollama model that writes the summaries; default `gemma4:26b`, null uses the generation model; it is unloaded after building and never used while answering; each new summary is checked for names its excerpt does not use and written again with the excerpt's names listed if needed), `query_translation` (default on, not used in `baseline` mode; `english_word_share`, default 0.6, skips the request when at least that share of the question's non-name words are ones the books use at least twice, `null` always asks; one generation request names the question's language and translates a non-English question into English, keeping names as written except translated forms of the novels' own names, which become the English edition's; the translation is searched alongside the question as asked and replaces it for the rewrites, name completion, reranking and scene search, while the answer model sees the question as asked; an English question is never reworded; prompt `rag-query-translation`), `answer_thinking` (let the generation model reason before writing the final answer; query transformations never think, and thinking tokens count against the output budgets); an empty reasoning answer is retried once without thinking), `name_completion` (default on; expand a bare first name or surname in the question to the two-word name the indexed passages predominantly use, when the passages use the other half of that name at least three times as often as the word itself, e.g. Mikael → Mikael Blomkvist; the completed question is searched separately, to `name_completion_hits` (300) hits since this one query does not enter fusion, and its hits join the wider pool, the wider pool is reranked against the completed question, and the admission bar also includes the best fused candidate scored against the completed question; fused candidates and the usual evidence keep their original-question scores; the answer model sees the completed question only when the evidence includes a passage that only the completed search found or one admitted through `wide_override_margin`, otherwise the question as asked), `rrf_constant`, the embedding/reranker/generation model identities, and generation temperature/context/output budgets. Managed prompt content is selected by Langfuse label and pinned per prompt version. Set `EVALUATOR_MODEL` to change the local Ollama judge model and optionally `EVALUATOR_OLLAMA_URL` to change its endpoint; reconcile the corresponding managed evaluator definition with `python app/prompt_assets.py --create-new-versions` before running, since preflight rejects model/config drift. For a controlled comparison, hold dataset snapshot, prompt/evaluator versions, models, and other config fields fixed and change one selected variable at a time.

The HTTP trigger accepts Langfuse's `datasetName`/`datasetId` and `customPayload` fields. Custom payload fields are `variant_label`, `config`, optional `dataset_version`, `item_ids`, and `prompt_label`:

```json
{
  "datasetName": "QA.csv",
  "datasetId": "<Langfuse dataset id>",
  "customPayload": {
    "variant_label": "passages-600",
    "config": {"passage_chars": 600}
  }
}
```

The endpoint requires `X-Experiment-Trigger-Token`; configure the same `EXPERIMENT_TRIGGER_TOKEN` in Langfuse custom headers. If request signing is enabled, the endpoint validates the raw-body HMAC signature and timestamp using `LANGFUSE_WEBHOOK_SECRET`. It checks project/dataset access, queues the run, and returns `execution_id` and `status_url` without executing dataset items in the request. Poll `GET /experiments/{execution_id}` for state, item/scoring counts, manifest identifiers, and the Langfuse run URL. An optional `Idempotency-Key` makes transport retries return the existing execution.

Recover a failed or partial execution with an authenticated `POST /experiments/{execution_id}/retry`. It creates a new execution ID, copies the original dataset/config/prompt-label selection, and records `retry_of_execution_id`; it never reuses the old run identity. Running and completed executions cannot be retried through this endpoint.

`/ask/stream` returns the same work as newline-delimited JSON: a `trace` event, `status` (`answering` or `thinking`), `token` events as the answer is written, and a final `done` carrying the same result `/ask` returns (or `error`). The pipeline runs in a copied context so its Langfuse trace is the same as `/ask`'s, and it finishes even if the browser disconnects. The Express frontend requests it when the browser accepts `application/x-ndjson` and forwards tokens to the UI.

The single worker uses the Langfuse Python SDK's hosted-dataset experiment runner at concurrency 1. It pins a historical dataset snapshot before selecting item IDs, writes a canonical snapshot checksum, resolves Hugging Face model commit SHAs when available, records pipeline and evaluator identities separately, and stores per-item evidence, outputs, errors, scores, and rationales. RAG latency and evaluator latency are recorded separately. An interrupted running job is marked failed on worker startup; a retry creates a new execution.
